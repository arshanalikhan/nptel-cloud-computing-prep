Formula sheet

Numericals that keep coming back

Every run has had SLA availability, cloud vs owning cost, MapReduce/HDFS and VM migration problems. Each worked example below follows the method in NPTEL's own solutions.

SLA availability

scheduled = hours/day × days
NPTEL key: availability = 1 − down / (scheduled − down)
simple   : availability = 1 − down / scheduled
SLA met if availability ≥ promised %

PYQ18 h/day × 30 days = 540 h, outages 6 + T, promise 98%: (6+T)/(534−T) ≤ 0.02 → T ≤ 4.59, so T = 5 or 6 breaks the SLA.

Failed requests allowed = requests × (1 − success%). 10,000 × 0.5% = 50.

Lecture 11 defines availability as 1 − downtime/uptime, which is the NPTEL form. Both formulas usually give the same option; if the options are close, use the NPTEL form.

Your 202699% of 12 h × 30 days = 3.6 h. 99.9% of 720 h = 0.72 h ≈ 43 min.

Cloud vs owning (Cloudonomics)

U   = C / B         (utility premium)
P   = peak demand,  A = average demand
own : B_T = P × B × T
cloud: C_T = U × B × A × T = ∫ C·D(t) dt
cloud cheaper  ⇔  U < P / A

PYQP = 200, D(t) = 8t, B = 120, C = 150: own = 24,000T, cloud = ∫150·8t dt = 600T². Cloud cheaper when T < 40.

Hybrid is often best, and the key factor is the peak-to-average ratio. Utility pricing suits variable demand.

Your 2026Average 75, peak 225, U = 2.8: P/A = 3 > 2.8, so cloud is cheaper.

Demand, Cv and penalty

Cv = σ / |μ|
n independent demands → Cv shrinks by 1/√n
penalty ∝ ∫ |D(t) − R(t)| dt
  • Flat demand: penalty 0, periodic provisioning works
  • Linear demand: fixed-interval provisioning gives a constant penalty
  • Exponential demand: fixed interval falls behind exponentially, so the penalty is exponential (not linear)

MapReduce and HDFS

blocks(file) = ceil(size / block size)
small files still take 1 block each
replicas     = blocks × replication (default 3)
mappers      ≈ number of input splits

PYQA 2019 question says 6 files make "24 blocks" with 64 MB blocks. It only works as 8 blocks × 3 replicas, so X ≤ 64 MB and Y ≤ 64 MB both fit.

Rating-count problems: map emits (key, 1) only for rows that match, reduce sums per key. Keys with zero matches don't appear.

Your 2026700 MB with 128 MB blocks → 6 blocks → 6 map tasks. The Partitioner picks each key's reducer; the Combiner is optional and may run 0, 1 or many times.

VM migration time

non-live: total time = downtime = M / B
use binary units: 1 GB = 2^30 B, 1 MB = 2^20 B
1024 GB / 16 MB/s = 65,536 s ≈ 18.2 h
  64 GB /  8 MB/s =  8,192 s ≈ 2.3 h

PYQThe answer keys mark "18 h, 18 h" and "2 h, 2 h": pick the option where both numbers are equal and closest to M / B.

Live migration (pre-copy, post-copy) keeps downtime small. Pre-copy uses the most bandwidth.

Your 202632 GB at 16 MB/s = 32 × 1024 ÷ 16 = 2,048 s ≈ 34 min.

01L1–L5

Introduction to cloud computing

  • PYQNIST definition: 5 essential characteristics (on-demand self-service, broad network access, resource pooling, rapid elasticity, measured service), 3 service models, 4 deployment models. Distractors seen in "which is NOT…": latency, guaranteed zero downtime.
  • Evolution: distributed → cluster → grid → utility → cloud.
  • PYQDistributed systems: fault tolerance, resource sharing, scalability, heterogeneity, no global clock. P2P is close to a truly distributed application. Client–server: no virtualization, scales only to a point.
  • PYQCluster: interconnected stand-alone computers, close together, managed as one resource. Components: PCs/workstations/SMPs, OS, high-speed interconnect, middleware, parallel programming environment.
  • Grid: geographically spread, heterogeneous, loosely coupled, virtual organizations. Users in slides include crystallography and reactor simulations.
  • PYQUtility computing: a service-provisioning model; the provider supplies computing resources and infrastructure management, pay-per-use. Pricing depends on scale, payment frequency and commitments.
  • PYQCloud characteristics (slides): massive scale, homogeneity, virtualization, resilient computing, low-cost software, geographic distribution, service orientation, advanced security.
  • PYQService models: SaaS = Gmail, Google Docs/Sheets/Slides, Salesforce (the user maintains nothing, so "in SaaS only applications are maintained by the user" is false). PaaS = App Engine, Azure App Service, managed DBs (you manage app + data). IaaS = EC2, Compute Engine, VMs (you manage the OS upward).
  • PYQXaaS ("everything as a service") = service-oriented architecture/infrastructure + cloud.
  • Pros/cons: lower cost, elasticity, anywhere access vs needing a constant connection, latency, less control, security, lock-in.
  • Your 2026Your assignments asked these as scenarios: who manages the OS decides IaaS vs PaaS (EC2 where you patch the OS = IaaS). Grid = many administrative domains, loosely coupled; cluster = tightly coupled and co-located. Distributed systems do not guarantee lower latency per operation. Type-2 hypervisors run on a host OS (VirtualBox, VMware Workstation).

02L6–L10

Architecture, deployment models, virtualization, XML, web services

  • PYQPublic cloud: AWS, Azure, GCP. SLAs are default and restrictive. Private: Eucalyptus, OpenStack in your own DC, Amazon VPC. Community: shared by orgs with common compliance needs. Hybrid: private + public, cloud bursting.
  • PYQOn-site private cloud: bulk data import/export is limited by your own network capacity. Outsourced private cloud: check network dependency, SLAs, multi-tenancy/co-residency, and legal issues about where data lives.
  • PYQCloud stack terms: inside a cluster manager, computer managers are linked by a high-speed network. Data Object Storage (DOS) stores user credentials and is usually one per cloud.
  • PYQHypervisor = VMM. Type-1 bare-metal (Xen, ESXi, Hyper-V) has lower overhead; Type-2 hosted (VirtualBox, VMware Workstation).
  • PYQFull virtualization: unmodified guest, trap/binary translation. Para-virtualization: guest OS modified to make hypercalls; faster (speed is an advantage, not a drawback). Hardware-assisted: Intel VT-x / AMD-V.
  • PYQVM architecture goals (Popek–Goldberg): equivalence, resource control, efficiency. A gap between host CPU and guest CPU readings is normal overhead (context switches, memory management, I/O emulation).
  • PYQXML: derived from SGML. Well-formed = one root, properly nested and closed, case-sensitive, quoted attributes. A parser must stop and report an error on a document that isn't well-formed. Namespaces use the xmlns attribute (not "xmlsn"). Names can't start with a digit or "xml".
  • PYQParsers: DOM loads the whole tree; SAX pushes events (low memory, little control); StAX pulls events (low memory, you control the flow).
  • PYQWeb services = XML + HTTP. SOAP = message format; WSDL = description (portType = operations + messages); UDDI = registry for discovery. They help reuse components, solve interoperability and connect existing software, and pass firewalls over HTTP. They are not built for ultra-low latency.
  • PYQEDI has low errors and high accuracy; web services do similar work and are cheaper to implement.
  • PYQSOA roles: service provider, service requestor, service broker/registry (publish → find → bind).
  • Your 2026Full (hardware-assisted) virtualization runs the guest unmodified using VT-x/AMD-V; para-virtualization needs hypercalls. Pick DOM when you must randomly access and modify a document that fits in memory; SAX/StAX are forward-only streams. WSDL describes the interface, UDDI finds it. SOA: publish (provider → registry), find (requestor → registry), bind (requestor → provider).

03L11–L15

SLA, cloud economics, managing data, MapReduce, OpenStack

  • PYQSLA = formal contract between service provider and consumer. The SLA contains SLOs; KPIs aggregate into SLOs, not into the SLA.
  • PYQSLA contents: availability (% uptime), response time, MTTR, RTO/RPO, penalties/credits, monitoring. Not low-level implementation details such as the exact encryption algorithm.
  • SLA types: off-the-shelf / non-negotiable (public cloud) vs customized / negotiable. Multilevel SLA: corporate level, customer level, service level.
  • PYQMonitoring problem: "bias towards vendors" means the vendor picks the monitored parameters to its own advantage, hence trusted third-party monitoring.
  • PYQEconomics: CapEx → OpEx; utility pricing pays off with variable demand; cloud is cheaper when U < P/A; hybrid hinges on peak-to-average ratio. See the formula sheet.
  • PYQParallel databases: shared memory, shared disk, shared nothing (tables partitioned across nodes; SQL optimizer handles distributed joins). Row store → OLTP; column store → data warehouse (e.g. Teradata).
  • PYQGFS: single master + chunkservers, 64 MB chunks, 3 replicas, master talks to chunkservers by heartbeat messages. HDFS: NameNode + DataNodes. BigTable: sparse sorted map (row, column, timestamp). Dynamo: key-value, eventual consistency.
  • PYQMapReduce: map takes key/value pairs and emits zero or more intermediate pairs; shuffle/sort groups by key; each reducer handles one key's list. Combiner = local mini-reduce that shrinks shuffle data; partition function picks the reducer; map tasks run where the data is.
  • PYQOpenStack: Nova = compute (manages ephemeral storage, which lasts until the VM is terminated; nova-scheduler picks the host); Neutron = networking (IP, gateway, DNS, L2; DHCP agent); Cinder = block storage; Swift = object storage; Glance = images; Keystone = identity/authentication; Horizon = dashboard; Heat = orchestration; Ceilometer = telemetry.
  • Your 2026Multilevel SLA = corporate + customer + service level. The official key says the provider is bound by the service-level SLA, the most specific one. 99.9% of 720 h = 0.72 h. Sub-second fraud detection needs streaming (Kafka + Flink, Kinesis, Pulsar); a nightly batch job is the wrong choice. Spark over petabytes reads from object storage (S3/GCS). 640 CPUs × 5 = 3,200 vCPUs.

  • PYQAzure is Microsoft's public cloud. The App Service plan is the hosting container for Web, API, Mobile and Function apps (region, instance size and count, pricing tier). It does not define security.

Storage = Cloud Storage (object, global edge caching), Cloud SQL (managed MySQL/PostgreSQL), Datastore/Firestore (NoSQL), Bigtable, Spanner. Google APIs let you integrate Google services into your app. Storage class for hot, worldwide content: multi-regional / Standard; Nearline for infrequent access.

GCP: Spanner for global relational data; GKE manages Kubernetes clusters, Cloud Run needs none; Pub/Sub → BigQuery → Looker Studio for IoT dashboards; gcloud app services set-traffic default --splits=v3=1 sends all traffic to v3. OpenStack: a Cinder volume survives VM deletion; Neutron routes tenant traffic. Several of these are not in the lecture transcripts, so expect some general cloud knowledge.

Cloud security

  • PYQBasic components: confidentiality, integrity, availability (not reliability or efficiency). Also authenticity and non-repudiation.
  • PYQAttack → property:
    AttackBreaksThreat class
    Interception / snoopingConfidentialityDisclosure
    ModificationIntegrityDeception, disruption, usurpation
    Interruption / DoSAvailabilityDisruption (and usurpation)
    Fabrication / replay of a tokenAuthenticityDeception
    Spoofing / masqueradeAuthenticityDeception + usurpation
    Repudiation of origin, denial of receiptNon-repudiationDeception
  • PYQPassive attacks: release of message contents, traffic analysis. Active: masquerade, replay, modification, DoS.
  • PYQAuthentication = verifying identity; authorization = deciding whether an operation is allowed. An IDS raises alerts on suspected attacks. Digital signatures (sender's private key) give non-repudiation. Penetration testing exploits weaknesses and needs written authorization.
  • PYQGartner's cloud risks: privileged user access, regulatory compliance & audit, data location, data segregation, recovery, investigative support, long-term viability (vendor lock-in, provider bankruptcy).
  • PYQSwitch provider when: it goes bankrupt or shuts the service down (also unacceptable price rises or quality drops).
  • PYQCo-residence attacks on EC2: map the cloud with nmap, hping (TCP SYN traceroute) and wget; side channels can extract RSA and AES keys.
  • PYQRogue hypervisor rootkits hide from malware detection and open covert channels to dump unauthorized code. Web-service attacks: injection, flooding (DoS), XSS, WSDL/metadata spoofing.
  • Collaborative SaaS: access control across domains, role mapping, trust; risk-based access control. Cloud broker: ranks providers by QoS, trust and price for the customer.
  • PYQFault tolerance: replication = keeping consistent copies on disks in separate physical locations.
  • Your 2026A bug that changes data breaks integrity; a fake login page breaks authenticity before anything leaks. Active: session hijacking, replay, man-in-the-middle, masquerade, DoS. Passive: sniffing, eavesdropping, traffic analysis, monitoring. Reconnaissance = DNS enumeration, port scans, OSINT (exploiting a bug is a later phase). Custom kernel module → IaaS. Backups replicated abroad → data location. Open standards and portable tech reduce lock-in.

07L31–L35

Mobile cloud, fog computing, geospatial cloud

  • PYQMCC components: Profiler monitors execution (time, power, network traffic); Solver decides which parts run on the phone vs the cloud; Synchronizer collects split results and hides the split from the user.
  • PYQMCC features: fewer device resources used, services reached through APIs, better reliability (cloud backup), faster app development; lower running cost for compute-heavy apps; some services run on the device and some in the cloud.
  • PYQCloudlet: small data center near users (campus, stadium). One hop away over Wi-Fi/short-range radio, so lower latency and battery use. "Multi-hop" is the trap.
  • MCC challenges: depends on WAN conditions, bandwidth, latency, security of data in transit. Offloading decisions use bandwidth/RTT, battery left, local CPU time.
  • PYQFog devices: cellular base stations, routers, switches, Wi-Fi gateways (they can run applications). Enablers: virtualization and SOA.
  • PYQFog benefits: low latency and location awareness, wide geographical distribution, very many nodes, heterogeneity, mobility support, real-time apps, less data moving across the network. Traps: homogeneity, immobility, "higher response time than cloud".
  • PYQHops: cloud = multiple hops, fog = one hop.
  • PYQGeospatial cloud: integrates heterogeneous back-end data services that can be inside or outside the cloud. Geographic info is static or dynamic and varies in scale; city population is dynamic. Enterprise GIS instances: resource, data and interface services.
  • PYQInteroperability levels: data, service (ability to exchange information to be consumed), security.
  • Your 2026Never offload millisecond safety tasks (collision avoidance) to a distant cloud. Dynamic offloading balances execution time, energy and utilization. Under 20 ms → cloudlet. Fog fixes the latency of distant data centers, and fog nodes don't store everything permanently. Splitting a raster into tiles needs boundary handling between neighbouring tiles.

08L36–L40

Docker intro, green cloud, sensor cloud, IoT cloud

  • PYQDocker parts: image = read-only template (filesystem layers + metadata); container = runtime instance of an image; Dockerfile = build recipe; Docker Engine/daemon builds images and runs containers; client (CLI) talks to the daemon over a REST API; Docker Hub = public registry; private registry also stores images; Compose = multi-container apps.
  • PYQCommands: docker ps running, docker ps -a all, docker images, docker rmi deletes an image, docker rm deletes a container, docker pull/push/run/build.
  • PYQVMs vs containers: VMs reach hardware through a hypervisor and carry their own kernel; containers share the host kernel and are isolated by namespaces + cgroups. Volumes outlive containers; the writable layer dies with the container.
  • PYQGreen cloud: PUE = total facility power / IT equipment power. A green broker schedules apps to cut energy. Consolidate VMs and power off idle hosts; DVFS.
  • PYQSensor cloud: lets sensor networks spread over a large area be used by many users on demand. The sensor-cloud proxy exposes sensors as cloud services; the network is still managed from the sensor-cloud interface through a sensor network proxy. In plain WSNs sensor data is not easily shared. Sensors are too weak for full virtualization, so virtual sensors aggregate physical ones.
  • PYQIoT platform building blocks: things, gateway, network & cloud. Vehicles lending networking and processing to other vehicles = IaaS.
  • Your 2026docker network ls lists networks; docker rmi removes images. etcd stores Kubernetes cluster state. Type-1: ESXi, Xen, Hyper-V Server; Type-2: VirtualBox. Sensor-cloud middleware abstracts heterogeneous sensors. Encrypt IoT data in transit (TLS). Edge cuts latency but never to zero.

09L41–L44

Cloud–fog–edge, resource management, cloud federation

  • PYQReal-time trap: "fog supports real-time interaction but cloud doesn't" is false (both do); "fog reduces latency vs cloud" is true.
  • PYQCloud–fog model: three layers (client/edge, fog, cloud). Fog servers hold a fog server manager + VMs using server virtualization; fog VMs report to the fog server manager; if fog lacks resources the request goes to the cloud.
  • PYQResource-management algorithms: discovery, benchmarking (measures CPU/storage/network performance), load balancing, placement.
  • PYQService-placement taxonomy: control plane design (centralized/distributed), placement characteristic (online/offline), system dynamicity (static/dynamic), mobility support.
  • PYQOffloading: moves server, app and data to the edge; augments user devices. Cloud → edge by server offloading; device → edge by application partitioning.
  • Placement rule: edge → fog → cloud by distance. Time-critical work at edge/fog (an autonomous car brakes at the edge); heavy, delay-tolerant work in the cloud.
  • PYQFederation benefits: maximize resource utilization, minimize power, load balancing, global utility, wider footprint. "Minimize utilization / maximize power" are the traps.
  • PYQFederation coupling: loosely coupled (little control, no advanced features); partially coupled (CSPs agree on terms for using each other's resources); tightly coupled (cross-site networks, cross-site VM migration).
  • PYQFederation architectures: hybrid/bursting (private + public for peaks), broker, aggregated (partner clouds pool resources into a bigger virtual infrastructure), multiplier. Interop via open standards (OCCI, CIMI, REST); trust via federated identity + enforced SLAs.
  • Your 2026Edge = immediate local action (per machine or camera); fog = regional aggregation (plant, roadside unit); cloud = global orchestration, history, model training. The earlier you filter, the less raw data reaches the cloud (edge < fog < cloud-only). More RAM/CPU on the same node = vertical scaling. Users moving between edge servers → service migration at handover. A broker finding a second CSP = federation; trust matters because providers are independent.

10L45–L50

Cloud/VM migration, containers, Docker, Kubernetes

  • PYQVM migration moves running VMs/apps from one physical host to another. Reasons in the key: take a physical machine out of service, relieve congested hosts.
  • PYQNon-live: suspend, copy, resume; total time = downtime = memory / bandwidth (see formula sheet). Live: pre-copy (copy memory in rounds while running, then a short stop-and-copy; uses the most bandwidth) and post-copy (move CPU state first, fetch pages on demand; each page sent once).
  • PYQLive migration costs: across distant DCs, latency and bandwidth variability matter most; energy rises with re-sending dirty pages.
  • PYQContainers: lightweight virtualization packaging code + all dependencies; no full guest OS; higher density, weaker isolation than VMs.
  • PYQDocker advantages: facilitates microservices, packages software, models networks; builds are reproducible, which helps continuous delivery. Private registry stores images; daemon + REST API + client.
  • PYQKubernetes: orchestrates, schedules, scales and restarts containers across a cluster. Workers are nodes; pods are the smallest deployable unit; it works at container level, not hardware level (it provides no hypervisor).
  • Your 2026A higher page-dirtying rate makes live migration longer; compression and deduplication cut the data sent. Post-copy starts the VM at the destination first. kube-scheduler places pods, kubelet runs them, kube-proxy handles service networking. Dockerfile → docker build → image → docker run → container. Namespaces isolate; cgroups limit resources. 32 GB at 16 MB/s ≈ 2,048 s ≈ 34 min. Named volumes survive container deletion.

11L51–L55

Dew computing, serverless / FaaS, sustainable cloud

  • PYQDew computing: on-premises computers provide functions that are independent of cloud services and collaborative with them. Works offline, syncs later (cloud-side sync resolves conflicts). Trade-off: local autonomy vs consistency. Fits places with patchy internet.
  • PYQServerless = FaaS + BaaS. Event-driven, stateless, short-lived functions; not always running (events start them); limited run time (AWS Lambda max 15 min); cold starts; local storage is ephemeral.
  • PYQControl: PaaS gives developers more control over the deployment environment than serverless. Cloud computing's focus was sysadmins; serverless focuses on programmers.
  • PYQAWS Lambda: Lambda layers share libraries and custom runtimes; log streams hold custom logging (not "runtimes"). BigQuery = Google's serverless warehouse; Redshift = AWS warehouse.
  • PYQSustainable cloud: cloud data centers have chassis and racks of servers; VMs/workloads can move to a remote CDC to balance load. Research areas include application design, capacity planning, renewable energy, cooling, energy and thermal management. "Environment sandboxing" is not one.
  • Your 2026Dew = local independence + later sync, with conflict detection and resolution on reconnect. Cold start = environment setup delay. Lambda's 15-minute cap rules out 40–45 minute jobs in one call. Independent invocations scale horizontally. Redshift = AWS's distributed data warehouse.

  • PYQ5G: eMBB (very high data rates, lower cost per bit), URLLC (low latency, high reliability), mMTC (massive IoT). MCC for 5G: shared resources and better reliability. Providers should offer full end-to-end orchestration with defined SLAs, self-service and automation.
  • PYQCPS: sensors → control → actuators in a closed loop. A CPCC framework is a system environment that builds and provisions CPS from cloud computing-based sensor, processing, control and data services.
  • PYQSpatial cloud: shared resource pooling for participating organizations; geospatial data (maps, coordinates, satellite images); disaster management and weather. A spatial trajectory is the time-ordered points of a moving object. Mobility analytics runs on the cloud; an ITS's key aspect is efficient mobility; V2V shares safety data over DSRC / IEEE 802.11p.
  • PYQIoHT: wearables → fog/edge gateway → cloud analytics. In fog, latency is fixed because application modules sit at the Area Gateway. Fog–edge reduces network congestion.

Vehicle sensors (edge) + roadside units (fog) + fleet analytics (cloud). 5G: eMBB high data rates (video, AR), mMTC massive IoT, URLLC ultra-reliable low latency.

Last-minute traps

Each line is a statement that past answer keys turned on. If you can say why each is right, you are ready.

  • KPIs → SLOs, and the SLA contains SLOs. "KPIs aggregate to SLA" is false.
  • Cloud is cheaper when U < P/A, not greater.
  • Public cloud SLAs are default and restrictive.
  • Utility pricing depends on scale, frequency and commitments.
  • Client–server: no virtualization, limited scaling.
  • Para-virtualization is faster; its cost is modifying the guest OS.
  • Namespace attribute is xmlns. Parser stops on non-well-formed XML.
  • Web services platform = XML + HTTP; UDDI = registry; WSDL portType = operations + messages.
  • Ephemeral storage → Nova, lasts until the VM is terminated. Block → Cinder, object → Swift, identity → Keystone.
  • GFS master ↔ chunkservers by heartbeat. SQL-scaling parallel DB = shared nothing.
  • BigQuery = app services, App Engine = compute, Cloud SQL = storage.
  • App Service plan does not define security. Deployment password ≠ portal password.
  • RL control policy → adaptation; network queueing → provisioning; multi-agent → allocation.
  • Performance/watt does not follow Moore's law. Power vs cores is nonlinear.
  • Fabrication → authenticity; interception → confidentiality; modification → integrity; interruption → availability.
  • Spoofing = deception + usurpation. Replay and DoS are active attacks.
  • hping = TCP SYN traceroute for co-residence mapping.
  • Cloudlet = single hop. Cloud = multi-hop, fog = one hop.
  • Fog benefits include heterogeneity and mobility, never homogeneity or immobility.
  • Both fog and cloud support real-time; fog just has lower latency.
  • Docker Hub = registry; Engine builds and runs; Compose = multi-container.
  • docker rmi deletes an image; docker ps -a lists stopped containers too.
  • VMs use a hypervisor; containers use namespaces + cgroups and share the kernel.
  • PUE = total facility / IT power.
  • Sensor data is not easily shared in plain WSNs. IoT blocks: things, gateway, network & cloud.
  • Tightly coupled federation = cross-site networks + VM migration; partially coupled = agreement on terms.
  • Federation benefits: maximize utilization, minimize power.
  • Pre-copy and post-copy are live migration. Non-live: downtime = total time.
  • Kubernetes works at container level; workers are nodes.
  • Serverless = FaaS + BaaS; PaaS gives more control than serverless.
  • FaaS functions have time limits (Lambda 15 min) and are not always running.
  • Lambda layers = shared libraries/runtimes; log streams = custom logging.
  • Dew = independent of and collaborative with the cloud.
  • "Environment sandboxing" is not a sustainable-cloud research category.
  • Area Gateway → latency fixed in fog. Fog–edge reduces congestion.
  • ITS key aspect = efficient mobility. eMBB = high data rates, lower cost per bit.
  • Multilevel SLA = corporate + customer + service; the provider is bound by the service-level one.
  • Full virtualization: guest unmodified (VT-x/AMD-V). Para: guest modified, hypercalls.
  • DOM = random access and edits in memory; SAX/StAX = forward-only streams.
  • Partitioner picks the reducer; Combiner is optional (0, 1 or many runs).
  • Session hijacking is active; eavesdropping and sniffing are passive.
  • Fake login page = authenticity; a bug changing balances = integrity.
  • More RAM/CPU on the same node = vertical scaling; more nodes = horizontal.
  • kube-scheduler places pods; etcd stores cluster state; kubelet runs pods.
  • docker build → image → docker run → container. Namespaces isolate, cgroups limit.
  • eMBB = video/AR bandwidth; mMTC = massive IoT; URLLC = low-latency control.
